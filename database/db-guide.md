# データベース解説書（非エンジニア向け）

**システム名:** 快活フロンティア 発注管理・予算管理システム
**作成日:** 2026-03-26
**対象読者:** ITに詳しくない業務担当者・管理者の方

---

## 1. はじめに

このシステムでは、店舗の発注業務（修理・備品・部品）と予算管理に必要なデータを管理しています。

**Excelで例えると**、22個のシートがあるExcelブックをイメージしてください。それぞれのシートには決まった項目（列）があり、業務で発生するデータが1行ずつ記録されていきます。

この22個のシートは、大きく3つのグループに分かれています。

| グループ | シート数 | 役割 |
|---------|---------|------|
| 基本情報の管理簿 | 10個 | 店舗・商品・ユーザーなど、めったに変わらない「土台」の情報 |
| 業務データの管理簿 | 10個 | 日々の発注・予算など、毎日増えていく「活動記録」 |
| システム運用の管理簿 | 2個 | 発注番号の採番や予約更新など、裏方の仕組み |

以降、それぞれの管理簿について「何を管理するのか」「なぜ必要なのか」を説明します。

---

## 2. 基本情報の管理簿（10個）

基本情報の管理簿は、発注業務の「土台」となるデータです。商品の名前や店舗の情報など、頻繁には変わらない情報を管理します。これらがないと、発注を入力するときに「どの店舗？」「どの商品？」と毎回手入力しなければならなくなります。

---

### 2-1. ゾーン管理簿（zones）

**何を管理するか:** 「東日本」「西日本」のような大きな地域区分

**なぜ必要か:**
全国の店舗を管理するとき、いきなり数十〜数百の店舗を一覧で見るのは大変です。まず「東日本 / 西日本」のような大きなくくりで分けることで、目的の店舗を素早く見つけられます。この管理簿がないと、店舗の絞り込みができず、全店舗を毎回一覧から探すことになります。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| ゾーンコード | 文字（3文字まで） | 「100」「200」などの識別番号 |
| ゾーン名 | 文字（50文字まで） | 「東日本」「西日本」などの名前 |
| 有効/無効 | はい/いいえ | 現在使われているかどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「地域マスタ」シートのようなもの。A列にコード、B列に名前...と項目が並び、東日本・西日本などが1行ずつ登録されます。

**他の管理簿との関係:** エリア管理簿と紐付いています（ゾーンの下にエリアがぶら下がります）。

---

### 2-2. エリア管理簿（areas）

**何を管理するか:** 「北海道」「東北」「関東」のような中くらいの地域区分

**なぜ必要か:**
ゾーン（東日本・西日本）だけでは、まだ店舗が多すぎて探しにくい場合があります。エリアで「関東」「東北」のようにもう一段階細かく分けることで、より効率的に店舗を管理できます。この管理簿がないと、ゾーンから一気に全店舗を見なければなりません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| エリアコード | 文字（3文字まで） | 「101」「102」「201」などの識別番号 |
| エリア名 | 文字（50文字まで） | 「北海道」「東北」などの名前 |
| 所属ゾーンコード | 文字（3文字まで） | どのゾーンに属するか |
| 有効/無効 | はい/いいえ | 現在使われているかどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「エリアマスタ」シート。ゾーン管理簿のコードを使って「このエリアはどのゾーンに属するか」を記録しています。VLOOKUPで参照先を引っ張るイメージです。

**他の管理簿との関係:** ゾーン管理簿と紐付いています（上位）。店舗管理簿と紐付いています（下位：エリアの下に店舗がぶら下がります）。

---

### 2-3. 店舗管理簿（shops）

**何を管理するか:** 各店舗の基本情報

**なぜ必要か:**
このシステムの中心となる管理簿です。発注は「どの店舗から出されたか」が必ず必要ですし、予算管理も店舗単位で行います。この管理簿がないと、発注も予算管理もできません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 店舗コード | 文字（5文字まで） | 「10301」などの識別番号 |
| 店舗名 | 文字（50文字まで） | 「○○店」などの名前 |
| 短縮コード | 文字（3文字まで） | 「S01」など。発注番号を作るときに使う短い記号 |
| 所属エリアコード | 文字（3文字まで） | どのエリアに属するか |
| 有効/無効 | はい/いいえ | 現在営業中かどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「店舗一覧」シート。全店舗の基本情報が一覧になっています。他のシートから「この店舗コードの店舗名は？」と参照される、最も重要なシートです。

**他の管理簿との関係:** エリア管理簿と紐付いています（上位）。ユーザー管理簿・発注管理簿・予算管理簿・自店調達申請管理簿・店舗カテゴリ管理簿と紐付いています（下位）。

### 2-4. カテゴリ管理簿（categories）

**何を管理するか:** 「フィットネス」「インドアゴルフ」などの業態分類

**なぜ必要か:**
店舗によって扱う業態が異なります。発注や商品を業態ごとに分類することで、「フィットネス関連の発注だけ見たい」「ゴルフ用品だけ表示したい」といった絞り込みが可能になります。この管理簿がないと、全ての発注や商品がごちゃ混ぜになってしまいます。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| カテゴリコード | 文字（20文字まで） | 「fitness」「golf」などの識別名 |
| カテゴリ名 | 文字（50文字まで） | 「フィットネス」「インドアゴルフ」などの表示名 |
| 有効/無効 | はい/いいえ | 現在使われているかどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「カテゴリ一覧」シート。業態の種類をまとめたシンプルなリストです。

**他の管理簿との関係:** 店舗カテゴリ管理簿・商品管理簿・発注管理簿・自店調達申請管理簿と紐付いています。

---

### 2-5. 店舗カテゴリ管理簿（shop_categories）

**何を管理するか:** 「どの店舗がどの業態を扱っているか」の組み合わせ

**なぜ必要か:**
1つの店舗がフィットネスとインドアゴルフの両方を扱うこともあります。店舗管理簿に業態を直接書くと1つしか書けませんが、この管理簿を使えば「A店 × フィットネス」「A店 × ゴルフ」のように複数の組み合わせを登録できます。この管理簿がないと、複数の業態を扱う店舗を正しく管理できません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 店舗コード | 文字（5文字まで） | どの店舗か |
| カテゴリコード | 文字（20文字まで） | どの業態か |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「店舗×カテゴリ対応表」シート。A列に店舗コード、B列にカテゴリコードが並び、1行が1つの組み合わせを表します。同じ店舗コードが複数行にあれば、その店舗は複数の業態を扱っているということです。

**他の管理簿との関係:** 店舗管理簿とカテゴリ管理簿の両方と紐付いています。この管理簿が両者を橋渡ししています。

---

### 2-6. 仕入先管理簿（suppliers）

**何を管理するか:** 備品の仕入先（取引先の会社）の情報

**なぜ必要か:**
備品を購入するには仕入先が必要です。仕入先の連絡先や担当者名をまとめて管理しておけば、発注のたびに「あの会社の電話番号は...」と探す手間が省けます。この管理簿がないと、仕入先の情報がバラバラになり、問い合わせ先が分からなくなります。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 仕入先ID | 数字（自動で付番） | システムが自動的に振る番号 |
| 仕入先名 | 文字（100文字まで） | 会社名 |
| 仕入先コード | 文字（20文字まで） | 社内で使う識別コード（任意） |
| 担当者名 | 文字（100文字まで） | 先方の担当者名（任意） |
| 電話番号 | 文字（20文字まで） | 連絡先電話番号（任意） |
| メールアドレス | 文字（100文字まで） | 連絡先メール（任意） |
| 有効/無効 | はい/いいえ | 現在取引があるかどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「仕入先一覧」シート。取引先の連絡帳のようなものです。

**他の管理簿との関係:** 商品管理簿と紐付いています（「この商品はどこから仕入れるか」を参照します）。

---

### 2-7. 商品管理簿（products）

**何を管理するか:** 備品発注で選べる商品のカタログ情報

**なぜ必要か:**
店舗が備品を発注するとき、商品名・価格・仕入先などを毎回手入力するのは非効率ですし、入力ミスも起きます。あらかじめ商品カタログとして登録しておけば、発注時に一覧から選ぶだけで済みます。この管理簿がないと、備品発注のたびに全ての情報を手入力しなければなりません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 商品ID | 数字（自動で付番） | システムが自動的に振る番号 |
| 商品名 | 文字（100文字まで） | 商品の名前 |
| 商品コード | 文字（20文字まで） | 「MAT-001」などの管理コード |
| 単価 | 数字（円） | 税込の価格 |
| 仕入先ID | 数字 | どの仕入先から買うか（任意） |
| カテゴリコード | 文字（20文字まで） | どの業態向けの商品か |
| おすすめ | はい/いいえ | おすすめ商品かどうか |
| 画像ファイルの場所 | 文字 | 商品写真の保存先（任意） |
| 商品説明 | 長い文字 | 商品の詳しい説明（任意） |
| 有効/無効 | はい/いいえ | 現在発注可能かどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「商品カタログ」シート。通販サイトの商品一覧ページをExcelにしたイメージです。

**他の管理簿との関係:** カテゴリ管理簿と紐付いています（業態別に分類）。仕入先管理簿と紐付いています（仕入先の参照）。商品画像管理簿・備品発注明細管理簿と紐付いています。

### 2-8. 商品画像管理簿（product_images）

**何を管理するか:** 商品の写真ファイルの情報（1商品あたり最大3枚）

**なぜ必要か:**
商品カタログに写真があると、店舗スタッフが「これが欲しい」と視覚的に確認できます。1商品につき複数の角度から撮った写真を登録できるようにするため、商品管理簿とは別の管理簿が必要です。この管理簿がないと、商品ごとに1枚しか写真を持てません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| ID | 数字（自動で付番） | システムが自動的に振る番号 |
| 商品ID | 数字 | どの商品の写真か |
| ファイルの場所 | 文字 | 画像ファイルの保存先 |
| メイン画像かどうか | はい/いいえ | 一覧画面で最初に表示する写真かどうか |
| 表示順 | 数字 | 写真を並べるときの順番 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「商品画像一覧」シート。A列に商品ID、B列に画像ファイル名が並びます。同じ商品IDが複数行あれば、その商品には複数の写真があるということです。

**他の管理簿との関係:** 商品管理簿と紐付いています（どの商品の写真かを参照）。

### 2-9. ユーザー管理簿（users）

**何を管理するか:** このシステムにログインする人の情報

**なぜ必要か:**
「誰がこの発注を出したか」「この人は管理者か店舗スタッフか」を判別するために必要です。また、ログインIDとパスワードで本人確認（認証）を行います。この管理簿がないと、誰でも自由にシステムを使えてしまい、不正な発注や情報漏洩のリスクが高まります。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| ユーザーID | 数字（自動で付番） | システムが自動的に振る番号 |
| ログインID | 文字（50文字まで） | ログイン時に入力するID（重複不可） |
| パスワード | 文字 | ログイン時のパスワード（暗号化して保存） |
| ユーザー名 | 文字（50文字まで） | 氏名など |
| 権限 | 「店舗」または「管理者」 | 店舗スタッフか管理者か |
| 所属店舗コード | 文字（5文字まで） | どの店舗に所属しているか（管理者は空の場合あり） |
| 有効/無効 | はい/いいえ | 現在ログインできるかどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「ユーザー一覧」シート。社員名簿にログイン情報と権限情報を加えたものです。

**他の管理簿との関係:** 店舗管理簿と紐付いています（所属店舗の参照）。発注管理簿・自店調達申請管理簿・予約更新管理簿と紐付いています（「誰が登録したか」の記録）。

### 2-10. システム設定管理簿（system_settings）

**何を管理するか:** システム全体の設定値（「設定名」と「設定値」のペア）

**なぜ必要か:**
「備品発注の締め曜日は水曜日」のように、システム全体に関わる設定をまとめて管理します。プログラムの中に直接書き込むのではなく、この管理簿に登録することで、設定変更のたびにプログラムを修正する必要がなくなります。この管理簿がないと、設定を変えるたびにシステムの改修が必要です。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 設定名 | 文字（50文字まで） | 何の設定かを表す名前（例：equipment_deadline_weekday） |
| 設定値 | 文字（255文字まで） | 設定の値（例：「3」= 水曜日） |
| 説明 | 文字（255文字まで） | この設定が何を意味するかの説明（任意） |
| 有効/無効 | はい/いいえ | この設定が有効かどうか |
| 表示順 | 数字 | 画面に表示するときの並び順 |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「設定一覧」シート。A列に設定名、B列に設定値が入った、とてもシンプルなシートです。

**他の管理簿との関係:** 他の管理簿とは直接紐付いていません。システム全体から参照される独立した設定集です。

**現在登録されている設定:**

| 設定名 | 設定値 | 意味 |
|-------|-------|------|
| equipment_deadline_weekday | 3 | 備品発注の締め曜日（0=日, 1=月, 2=火, 3=水, 4=木, 5=金, 6=土） |

## 3. 業務データの管理簿（10個）

業務データの管理簿は、日々の発注業務で発生するデータを記録するものです。基本情報の管理簿が「辞書」なら、業務データの管理簿は「日誌」のようなものです。毎日データが増えていきます。

---

### 3-1. 発注管理簿（orders）

**何を管理するか:** 修理・備品・部品、全ての発注に共通する基本情報

**なぜ必要か:**
このシステムの最も重要な管理簿です。「いつ・どの店舗が・何の種類の発注をして・今どういう状態か」を一元管理します。この管理簿がないと、発注の把握ができません。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 発注番号 | 文字（30文字まで） | 「REP-S01-20260301-0001」のように自動で付く番号 |
| 発注種別 | 「修理」「備品」「部品」のいずれか | 何の発注か |
| カテゴリコード | 文字（20文字まで） | どの業態の発注か |
| ステータス | 数字（0〜4） | 進捗状態（下記参照） |
| 発注元店舗コード | 文字（5文字まで） | どの店舗からの発注か |
| 発注日 | 日付 | 発注した日 |
| 見積金額 | 数字（円） | 見積もりの金額（任意） |
| 最終金額 | 数字（円） | 確定した金額（任意） |
| 納品予定日 | 日付 | 届く予定日（任意） |
| 実納品日 | 日付 | 実際に届いた日（備品のみ・任意） |
| 作成者 | 数字 | 発注を登録したユーザー |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**ステータス（進捗状態）の流れ:**

```
0:依頼中 → 1:手配中 → 2:手配済 → 3:納品待ち → 4:完了
```

| 番号 | 状態名 | 修理の場合 | 備品の場合 | 部品の場合 |
|-----|-------|-----------|-----------|-----------|
| 0 | 依頼中 | 店舗が依頼を出した | 店舗が依頼を出した | 店舗が依頼を出した |
| 1 | 手配中 | 業者と調整中 | 発注準備中 | 調達手配中 |
| 2 | 手配済 | 訪問日が確定 | 業者に発注済 | 業者に発注済 |
| 3 | 納品待ち | 修理作業中 | 入荷待ち | 入荷待ち |
| 4 | 完了 | 修理完了 | 納品完了 | 受取完了 |

**Excelで例えると:** 「発注一覧」シート。全ての発注が1行ずつ並び、ステータスで「今どの段階か」がひと目で分かります。

**他の管理簿との関係:** 店舗管理簿・カテゴリ管理簿・ユーザー管理簿と紐付いています。また、発注種別に応じて以下の詳細管理簿と紐付きます。
- 修理の場合 → 修理詳細管理簿・対応不可日管理簿・対応不可曜日管理簿
- 備品の場合 → 備品明細管理簿
- 部品の場合 → 部品詳細管理簿
- 全種別共通 → 写真管理簿・ステータス変更履歴管理簿

### 3-2. 修理詳細管理簿（order_repair_details）

### 3-5. 備品発注明細管理簿（order_equipment_items）

**他の管理簿との関係:** 発注管理簿と紐付いています（どの発注の明細か）。商品管理簿と紐付いています（どの商品か）。

### 3-10. 予算管理簿（budgets）

**何を管理するか:** 店舗ごと・月ごと・部門ごとの予算額と実績額

**なぜ必要か:**
「今月の予算はいくらで、今いくら使ったか」を管理するための管理簿です。予算オーバーを防ぎ、計画的な支出管理を可能にします。この管理簿がないと、各店舗の予算消化状況が見えず、いつの間にか使い過ぎてしまいます。

**※ この管理簿は「基本情報」と「業務データ」の両方の性質を持っています。**
- **基本情報としての面:** 年度の初めに管理者が各店舗の月ごとの予算額を登録（あらかじめ決まっている情報）
- **業務データとしての面:** 発注が完了するたびに実績額が加算されていく（日々変動する情報）

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| ID | 数字（自動で付番） | システムが自動的に振る番号 |
| 店舗コード | 文字（5文字まで） | どの店舗の予算か |
| 年度 | 数字 | 何年度か（例: 2026 = 2025年4月〜2026年3月） |
| 月 | 数字（1〜12） | 何月分の予算か |
| 部門 | 「全体」「フィットネス」「インドアゴルフ」のいずれか | どの部門の予算か |
| 予算額 | 数字（円） | その月に使える上限額 |
| 実績額 | 数字（円） | 実際に使った金額（発注完了時に自動加算） |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「予算管理表」シート。店舗×月×部門の組み合わせごとに、予算額と実績額が並んでいます。「今月あといくら使えるか」は「予算額 - 実績額」で計算できます。

**他の管理簿との関係:** 店舗管理簿と紐付いています（どの店舗の予算か）。

## 4. システム運用の管理簿（2個）

システム運用の管理簿は、利用者が直接目にすることは少ないですが、システムが正しく動くために裏側で使われている管理簿です。

---

### 4-1. 発注番号の連番管理簿（order_sequences）

**何を管理するか:** 発注番号を重複なく自動的に振るための連番カウンター

**なぜ必要か:**
発注番号「REP-S01-20260301-0001」の末尾4桁は連番です。同じ店舗・同じ日に複数の発注があったときに「0001」「0002」「0003」...と順番に番号を振る必要があります。この管理簿が「今、何番まで使ったか」を記憶しています。この管理簿がないと、発注番号が重複してしまう恐れがあります。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| 種別 | 文字（3文字まで） | REP（修理）、EQU（備品）、PTS（部品）、REQ（自店調達）のいずれか |
| 店舗コード | 文字（5文字まで） | どの店舗の連番か |
| 対象日 | 日付 | 何日分の連番か |
| 現在の連番 | 数字 | 今何番まで使ったか |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**Excelで例えると:** 「採番カウンター」シート。種別×店舗×日付ごとに「次は何番か」を管理するカウンターです。

**他の管理簿との関係:** 他の管理簿と直接紐付いてはいませんが、発注管理簿・自店調達申請管理簿の番号採番に使われます。

---

### 4-2. 予約更新管理簿（master_scheduled_changes）

**何を管理するか:** 「この日になったら、この基本情報をこう変更する」という予約

**なぜ必要か:**
例えば「来月1日から新店舗を追加したい」「4月から商品の価格を改定したい」という場合、事前に変更内容を予約登録しておけば、指定した日時に自動で反映されます。手作業で当日に変更する手間やミスを防げます。この管理簿がないと、変更のたびに管理者が手動で作業する必要があります。

**管理する項目一覧:**

| 項目名 | 種類 | 説明 |
|-------|------|------|
| ID | 数字（自動で付番） | システムが自動的に振る番号 |
| 対象の管理簿名 | 文字（50文字まで） | どの管理簿を変更するか |
| 操作の種類 | 「追加」「変更」「削除」のいずれか | 何をするか |
| 対象データの番号 | 文字（100文字まで） | どのデータを変更するか |
| 変更内容 | データ（JSON形式） | 何をどう変えるか |
| 反映予定日時 | 日時 | いつ反映するか |
| 反映実行日時 | 日時 | 実際に反映された日時（任意） |
| 状態 | 「反映待ち」「反映済み」「キャンセル」「エラー」のいずれか | 予約の現在の状態 |
| 登録者 | 数字 | 誰がこの予約を登録したか |
| 作成日時 | 日時 | このデータを登録した日時 |
| 更新日時 | 日時 | このデータを最後に変更した日時 |

**予約の状態の流れ:**

```
反映待ち → 反映済み（成功した場合）
         → エラー（失敗した場合）
         → キャンセル（管理者が取り消した場合）
```

**Excelで例えると:** 「予約変更一覧」シート。「いつ・どの管理簿の・どのデータを・どう変えるか」を事前に登録しておくリストです。

**他の管理簿との関係:** ユーザー管理簿と紐付いています（誰が予約を登録したか）。

---

```
     │      ││││↓ 写真   │
     │      │││↓ 履歴    │
     │      ││↓ 備品明細  │
     │      │↓ 部品詳細   │
     │      ↓ 修理詳細    │
     │        修理不可日   │
     │        修理不可曜日 │
     │                    ↓
     │              自店調達申請
     │
     └─────→ 予約更新
```

### 発注まわりの関係（分かりやすく整理）

```
【修理発注の場合】
  発注 ─┬─ 修理詳細（1件）
        ├─ 対応不可日（複数件）
        ├─ 対応不可曜日（複数件）
        ├─ 写真（最大3件）
        └─ ステータス変更履歴（複数件）

【備品発注の場合】
  発注 ─┬─ 備品明細（複数件） ── 商品カタログ
        ├─ 写真（最大3件）
        └─ ステータス変更履歴（複数件）

【部品発注の場合】
  発注 ─┬─ 部品詳細（1件）
        ├─ 写真（最大3件）
        └─ ステータス変更履歴（複数件）
```

## 6. よくある質問（FAQ）

### Q1. 管理簿を後から増やせますか？

**はい、増やせます。** システムの機能追加に合わせて、新しい管理簿を追加することができます。既存の管理簿に影響を与えることなく追加できるので、安心してください。

---

### Q2. 項目を増やしたい場合は？

**対応可能です。** 例えば「店舗に住所の項目を追加したい」といった要望があれば、既存の管理簿に新しい項目を追加できます。既に登録されているデータはそのまま残りますので、データが消える心配はありません。（技術的にはカラム追加で対応します。）

---

### Q3. データが間違って入った場合は？

**修正できます。** phpMyAdmin（データベースの管理画面）を使って、間違ったデータを直接修正することができます。ただし、データの修正は慎重に行う必要がありますので、管理者に依頼してください。

---

### Q4. 予約更新って何ですか？

**指定した日に自動で基本情報を更新する機能です。** 例えば「来月1日に新しい店舗を追加したい」という場合、今日のうちに変更内容を予約登録しておけば、指定した日時にシステムが自動で反映してくれます。事前にCSVファイルで一括登録することもできます。主な利用場面は以下の通りです。

- 新店舗の追加
- 店舗の統廃合
- 商品価格の改定
- マスタデータの一括更新

---

### Q5. 発注番号のルールは？

発注番号は以下のルールで自動的に付けられます。

```
種別-店舗コード-日付-連番
```

**例:**
- 修理発注: `REP-S01-20260301-0001`
- 備品発注: `EQU-S01-20260301-0001`
- 部品発注: `PTS-S01-20260301-0001`
- 自店調達申請: `REQ-S01-20260226-0001`

同じ店舗・同じ日に複数の発注があると、末尾の連番が `0001` → `0002` → `0003` と増えていきます。

---

### Q6. 「有効/無効」の項目は何のためにありますか？

ほぼ全ての基本情報の管理簿に「有効/無効」の項目があります。これは**データを完全に消すのではなく、「無効」にして非表示にする**ための仕組みです。例えば、閉店した店舗を「無効」にすれば、新規発注の画面には表示されなくなりますが、過去の発注データはその店舗の情報を参照できます。データを削除してしまうと過去の記録まで消えてしまいますが、「無効」にすれば履歴は残ります。

---

### Q7. 年度の考え方は？

予算管理の「年度」は日本の会計年度に基づいています。**「2026年度」は2025年4月〜2026年3月**を意味します。月は暦通りの1〜12月で管理します。
